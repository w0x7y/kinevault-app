# Account export and deletion

Settings → Your account → Export account data downloads a JSON file on web and opens the system file sharing sheet on iOS/Android. Native builds require the installed `expo-sharing` module. The temporary native export file is removed when sharing completes or fails.

The versioned `kinevault-track-account-export` format contains the current account ID, export time, logical tracking documents, local pending flags/revisions, cloud versions/revisions, conflict flags, recovered setup answers, photo metadata, and base64 JPEG contents. Profile documents include body-weight history when present. It excludes passwords, session tokens, auth storage, internal history manifests/fragments and other accounts' records. The local and cloud copies are retained independently so unsynced edits are never silently replaced. Cloud failures fail online exports; a successful empty response cannot replace known saved cloud history. Offline **Export device copy** explicitly marks cloud data as unchecked and retains any last-observed competing conflict copy. Photos from other devices cannot be included because photos are local only. Missing, unreadable or malformed photos/documents fail the export instead of silently dropping their contents. Repeated exports may differ if a device changes data between them; this is not a cross-device transactional backup.

The Account management attempt module owns Settings action exclusion, export preparation/delivery and confirmation fields. It reads identity directly from the live Account controller before delivery. Rejected deletion feedback clears on cancel or caller retirement. Feedback from an abandoned caller cannot appear in a replacement Settings view, and replacement owners retire delivery/navigation. A confirmed deletion still completes Account-owned cleanup and session retirement; its notice survives an auth-driven remount. The attempt preserves its final Account redirect when confirmed deletion itself detaches Settings, while earlier departure or restart suppresses it. A replacement account signing in and out during session clearing cannot revive the old deletion completion.

Deletion asks for the current password and the literal `DELETE`. The disclosure explains that KineVault apps share the login and that deleting it removes its shared account records, Track documents/history and membership. The button requires connectivity. Passwords exist only in the field/request memory, are cleared immediately on submission, and are never saved or logged.

The app coordinates deletion across every live store for the same local backend and owner. It freezes writes and new media operations, retires sync generations, and drains outstanding uploads, local writes, media imports/removals, and unfinished guest media work claimed by that account. It persists `deleted.v1 = "pending"` before making the server request. A rejected first request removes that marker and resumes surviving mounted stores; stopped stores stay stopped. If marker removal fails, data stays frozen. An interrupted earlier attempt also stays frozen after a later rejection because its server outcome is uncertain.

Confirmed server deletion marks the owner permanently blocked in memory, then persists `deleted.v1 = "1"` and removes owner-prefixed records/fragments, claimed guest recovery, and owned photos. Every write checks the persistent marker at its commit boundary. If the confirmation write fails, the already durable pending marker still blocks uploads and writes after restart. A later cleanup can retry using the surviving confirmed lifecycle; after restart, `cleanupDeletedData` requires a confirmed `"1"` marker. Pending markers never authorize physical cleanup by themselves.

The immutable storage owner lets cleanup finish after an account switch. Deletion uses an app-owned auth adapter to clear only the deleted owner's persisted login; it does not call SDK `signOut` after the server has already revoked sessions. Native clearing and all SDK session writes share a serialized storage transaction. Web SDK storage mutations share a Web Lock across tabs when available; clearing compares the persisted owner and removes the login synchronously within that critical section. A completed raw replacement made outside the adapter is also detected at removal time. Web Storage provides no compare-and-swap for a truly concurrent non-cooperative writer. Browsers without Web Locks refuse automatic current-owner session removal and report the device-cleanup error instead of risking another tab’s login. Storage notifications update mounted account controllers, including a replacement account discovered at clearing time. A confirmed deleted owner cannot write a late in-flight refresh back into that adapter. No private SDK methods or fields are used. The app retains one account controller per auth adapter across root-provider remounts, so the deletion notice survives rebuilding the account-owned navigator. A real replacement identity still clears the previous account’s feedback; a full document/app reload does not persist that notice.

Photo ownership is recorded separately in the local-only `kinevault-track.profile-media.v1.ownership.v1` document, listed in `localOnlyAccountDocumentKeys`. The ledger records allocated IDs before imports and existing IDs before metadata detaches them; failed physical removal retains those IDs. Imports reserve IDs against every owner's current metadata and orphan inventory, and the native/web file adapters reject existing physical IDs before creation. New media operations cannot start during deletion, and deletion waits for an already running import and its rollback before removing the inventory. Deletion includes both active metadata and these orphan records, protects IDs referenced by another owner's metadata or ledger, and retains recovery records when cleanup fails. The ledger remains on this device, is claimed with guest media, is never uploaded, and does not change the export's tracking documents or active-photo contents.

Cleanup protects other accounts, preferences, and unrelated guest data. Failure reports that server deletion succeeded and some data remains on this device. `cleanupDeletedData` supports a focused retry of confirmed cleanup; the current settings UI directs the user to clear this app's device/site storage. Historical physical orphans whose ownership was lost before this ledger existed cannot safely be assigned to an account and are not claimed as removed. Unreadable ownership evidence causes cleanup to fail instead of guessing which files belong to another owner. Other devices' local photos/caches must be removed on those devices too.

## Server rollout

No function or schema is deployed by this change. Deploy `supabase/functions/delete-account/index.ts` to the same verified Supabase project as the shared KineVault account. It imports pinned `@supabase/supabase-js@2.117.2` and requires the standard server environment variables `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY`. Never put the service key into an `EXPO_PUBLIC_*` setting or client bundle.

The checked-in `supabase/config.toml` keeps `verify_jwt = true` for this user-authenticated endpoint; preserve that configuration at deployment. The platform check is followed by the handler's live `getUser` authorization. See [Supabase authorization headers](https://supabase.com/docs/guides/functions/auth-headers). The handler bounds streamed input to 2,048 UTF-8 bytes before parsing, cancels oversized input, and returns a generic error for unreadable input. CI checks the Deno entry separately from Expo TypeScript.

The endpoint accepts only POST JSON `{password, confirmation: "DELETE"}` with a bearer token. It rejects extra fields, including any proposed victim ID. It validates the caller against Supabase Auth via `getUser(token)`, derives the verified email from Auth, signs in with that email/password using a fresh nonpersistent client, checks the reauthenticated ID equals the caller ID, calls `auth.admin.signOut(freshAccessToken, "global")`, then `auth.admin.deleteUser(callerId, false)`. Failed validation, revocation or deletion never returns `{deleted: true}`. CORS preflight is supported without cookies. Request bodies and credentials must never be logged at deployment.

Before enabling production deletion, audit **every** application's data associated with the shared account, including Storage objects and tables without `auth.users` foreign keys. The reviewed repository's profiles, roles, subscriptions, Track documents and partition rows use `ON DELETE CASCADE`; this endpoint relies on that ownership model. Add reviewed server cleanup for any additional shared-app data/storage found in the deployment inventory before claiming it is removed. Supabase Storage objects owned by a user can prevent Auth deletion; this build does not create cloud photo objects. Do not execute deletion against real users for a smoke test. Use a disposable user in an isolated local/staging project and verify refresh-token rejection, Auth absence and zero owned rows in every audited table.

Auth session revocation invalidates refresh sessions; already-issued access JWTs can survive until expiry. User deletion and ownership foreign keys prevent new Track rows for that deleted ID. Other sensitive APIs must validate current users/sessions as appropriate. See [Supabase admin signOut](https://supabase.com/docs/reference/javascript/auth-admin-signout), [deleteUser](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser), and [getUser](https://supabase.com/docs/reference/javascript/auth-getuser).

If the network response is lost after the server committed deletion, the client cannot claim success and retains its local data. The old account can no longer authenticate; remove remaining local data through device app/site storage settings. This is an intentional recovery boundary, not an automatic retry with a client-supplied account ID.

## Verification

`tests/account-management.test.ts` verifies logical export completeness, cloud/local failure handling, actual photo contents, owner-switch cancellation, freeze/drain ordering, failure recovery, protected photos, owner-scoped fragment cleanup, tombstone behavior, caller-derived server identity, password mismatch and revoke/delete failures. `tests/account-auth.test.ts` covers controller lifecycle and feedback. `tests/account-session-adapter.test.ts` exercises the installed Supabase SDK against a mocked HTTP endpoint and shared persisted storage: it reproduces the SDK HTTP logout race, verifies the deletion adapter preserves a replacement in both SDK contexts/storage/controller, tests replacement during native clearing and raw external web replacement, confirms ordinary deletion clears `getSession()` without HTTP logout, covers cross-tab Web Lock coordination and unsupported-lock failure, and verifies deletion feedback survives a provider remount and is cleared when B signs in. `tests/account-deletion-regressions.test.ts` covers multiple live A stores, A→B→A/remount races, writes against persistent markers, confirmation failure/restart behavior, stopped-upload draining, detached/unsaved/partially imported media, failed physical rollback, cleanup retry, claimed guest imports, other-owner inventory protection, ID collisions and unknown legacy orphans. Browser coverage verifies actual JSON download and JPEG contents without a live backend. No remote function deployment, real-user deletion, or physical-device cleanup check is part of this local verification.
